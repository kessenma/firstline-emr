## API Integration

### Endpoints Used

1. **GET /api/admin/GET/denied-users?page={page}&limit={limit}**
   - Fetches paginated list of denied users
   - Returns: `{ users: DeniedUser[], totalPages: number, currentPage: number }`
   - Filters: `authorized = false AND denialDate IS NOT NULL`
   - Ordered by: `denialDate DESC`

2. **POST /api/admin/POST/re-approve-users**
   - Reinstates (re-approves) denied users
   - Body: `{ userIds: string[] }`
   - Returns: `{ message: string }`
   - Sets `authorized = true` and clears `denialDate`

## User Flows

### Reinstate Single User Flow

1. User views denied users list
2. User taps "Reinstate" button on a card
3. Confirmation dialog appears with user name
4. User confirms action
5. System calls re-approve API
6. User removed from list
7. Success notification shown

**Error Scenarios:**
- API error → Show error message, keep user in list
- Network error → Show error with retry option
- Permission denied → Show appropriate error message

### Bulk Reinstate Flow

1. User views denied users list
2. User selects multiple users via checkboxes
3. User taps "Reinstate" button in bulk action bar
4. Confirmation dialog shows count of selected users
5. User confirms action
6. System calls re-approve API with all selected IDs
7. All reinstated users removed from list
8. Selection cleared
9. Success notification shown with count

**Error Scenarios:**
- Partial failure → Show error, re-fetch list to show current state
- Complete failure → Show error message, keep selections
- Network timeout → Show error with retry option

### Pagination Flow

1. User scrolls to bottom of list
2. System detects scroll position
3. If more pages available, triggers load more
4. Loading indicator shown at bottom
5. Next page data fetched
6. New users appended to list
7. Loading indicator hidden
